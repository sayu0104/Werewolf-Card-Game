# ブラウザ人狼ゲーム 要件定義書

## 1. プロジェクト概要

### 1.1 コンセプト
人狼ゲームとカードゲーム（デッキ系）を融合させたブラウザゲーム。
発言の"印象"（強気/弱気、疑う/擁護など）をフリーテキストではなくカードとして表現することで、
心理戦の駆け引きを戦略的なカードプレイに落とし込む。

### 1.2 目標
- **1人プレイ対応を最重要目標とする**（複数人プレイも将来的に対応）
- 疑似プレイヤー（キャラクター）が人数を補い、少人数でも人狼ゲームとして成立させる
- キャラクターごとに行動パターン・難易度・口調を作り込み、実際に複数人でプレイしているかのような体験を実現する

### 1.3 想定プレイスタイル
- 個人開発のポートフォリオとして、完成後にネット上へ公開予定
- 技術スタックはSpring Boot + MySQLを基本とする

### 1.4 AIに関する方針（重要）
- **当面、生成AI（LLM）は使用しない。** キャラクターの発言・行動はすべてルールベース（条件分岐＋パターン）で実装する
- 将来的に生成AIを使いたくなった場合は、その時点で改めて導入を検討する
- そのため、キャラクターの「戦略判断（どの行動を取るか）」と「表現（セリフ）」を分離した設計とし、表現部分をLLMではなく定型・パターンベースで作り込む
  - 戦略判断：被疑心ポイント・イベントログなどの構造化データに基づくロジック処理
  - 表現：あらかじめ用意したセリフパターンから、状況・キャラクターに応じて選択する

## 2. MVPスコープ

### 2.1 対応役職（MVP: 5役職）
| 役職 | 陣営 | 概要 |
|---|---|---|
| 村人 | 村人陣営 | 専用カードを持つ（詳細は今後検討） |
| 人狼 | 人狼陣営 | 夜に襲撃を行う。複数人いる場合はお互いを認識する |
| 占い師 | 村人陣営 | 対象を占い、結果は朝に判明する。占い師自身が死亡しても結果は判明する |
| 狩人 | 村人陣営 | 対象を護衛する。護衛は人狼の襲撃より優先処理される |
| 狂人 | 人狼陣営（人狼の正体は知らない） | 「偽占い」カードを持ち、場をかき乱す役割。自分の生死は勝敗に影響せず、人狼陣営の勝利が目的 |

> 将来的に第三陣営（妖狐など）の追加を想定し、役職割り振りシステムはそれに対応できる設計とする。

### 2.2 ゲーム進行フェーズ
1. **朝**：前夜の結果（襲撃・護衛・占い結果）が判明する。生存状況の変化に応じて勝敗判定を行う
2. **昼**：議論フェーズ。プレイヤーはカードを使って議論する（基本ターン制、複数人プレイ時はオプションで時間制）
   - 役職カード（占い・護衛・襲撃・偽占い）も、この昼のうちに「使うかどうか」を決めてコストを消費する。**対象の選択は夜に行う**
3. **投票**：全員同時投票。同票の場合は同数だった者同士で再投票。処刑確定後、勝敗判定を行う
4. **夜（2段階）**：
   - **夜1（意思決定）**：昼に使用を決めた役職カードについて、対象者を選ぶ。人狼が複数いる場合はここで襲撃対象をすり合わせる。全役職が同時に選択するため、「悩んで沈黙する人＝人狼」という消去法を防げる
   - **夜2（処理）**：護衛・襲撃の対象重複判定など、すべての結果処理を裏側で実行する。結果は翌朝まで本人にも公開されない

> 役職カードの「使用（コスト消費）は昼／対象選択は夜」という分離により、昼のコストバランスを崩さずに夜の意思決定時間を確保する。
> 昼にカードを使わなかった場合、その夜は何も発動しない。

### 2.3 処刑・勝敗
- 処刑者の役職は**非公開**とする（将来の霊媒師追加に備える意味もある）
- 処刑確定後、処刑者に最後の発言機会（遺言システム）を与える（カード使用は不可、テキストのみ）

### 2.4 勝利条件
- 村人陣営：村人・占い師・狩人／人狼陣営：人狼・狂人
- **村人陣営の勝利**：生存する人狼が0人になる
- **人狼陣営の勝利**：生存する人狼の数 ≧ 生存する村人陣営の数
- 狂人自身の生死は勝敗判定に影響しない（陣営の勝敗がそのまま狂人の勝敗になる）
- 判定タイミング：朝（夜の結果反映後）と投票後（処刑確定後）。「生存状況が変化するたびに都度判定する」設計とし、将来的に昼など別タイミングでの判定が必要になっても対応できるようにする

## 3. カードシステム

### 3.1 カードの分類
- **役職カード（保証枠）**：占い・護衛・襲撃・偽占いなど。毎ターン確実に手元にあり、コストを払って使用する
- **希少カード（保留枠）**：人狼の「疑いを逸らすカード」など、1ゲーム内の使用回数に制限があるカード。ドローの対象外とし、使うまで手札に残り続ける
- **基本カード（山札制ドロー枠）**：疑う・擁護・疑いをそらす、など。個人ごとの山札→手札→捨て札のローテーションで、毎ターン一定枚数を引く

### 3.2 カード公開ルール
- カードを「使った」こと自体は全役職共通で他プレイヤーに見える
- 何のカードを使ったかは、役職カード（占い・護衛など）は非公開とし、「疑う」など基本カードは役職ごとに公開/非公開を設定する

### 3.3 コストルール
- 1ターンあたりの**共通コストプール制**（仮上限5）を採用
- 占いカード（占い師・コスト1・強制使用）
- 偽占いカード（狂人専用・コスト1・任意使用）
- 護衛カード（狩人・コスト1以上。コスト0にはしない＝毎ターン確実な護衛を避ける）
- 襲撃カード（人狼専用・コスト3（仮、要調整）。共通プール上限5に対して重すぎない値にする。当初の仮4は重すぎると判断）
- 疑う/擁護カード：弱=コスト1／中=コスト2／強=コスト3（仮）
- 占いカードは当初コスト0を検討したが、「コスト0の強制枠＋残りコスト」で占い師だけ使用可能枚数が突出し役職バレにつながるため、コスト1に変更して他役職と最大枚数を揃える（コスト以外に枚数上限を追加する二重管理案は複雑すぎるとして不採用）

### 3.4 占い・偽占いカードの仕様
- 対象選択は都度記録・固定するが、結果（白/黒）の解釈は申告（CO）時に1回だけ確定する（一度申告した内容は以降変更不可）
- 「占い師申告（CO）」は誰でも使える発言アクション（コストなし）。自分が持つ記録（本物/偽物）を任意のタイミングで公開する。申告時に被疑心が変動する等の副作用の有無は未確定
- 本物の占い師の占いカードはコスト1・強制使用／狂人の偽占いカードはコスト1・任意使用
- 占い師・狂人の対象選択タイミングは、他役職と同様に夜に統一する（足跡を揃え、見分けをつきにくくするため）

### 3.5 打ち消し・妨害要素
- 「役職能力そのものを無効化」案、「誤情報カード」案は不採用
- 「人狼複数時の護衛突破カード」案は採用候補（人狼の襲撃人数ルールと連動して要決定、6章参照）
- 基本カード同士の打ち消し（「疑い5」を「疑いをそらす5」で相殺）はMVPに含む

### 3.6 基本カードの山札
- 山札は1ゲーム（想定ターン数）でおおよそ1巡するように総枚数を設計する（弱いカードのみを引き続ける理不尽を構造的に防ぎ、「山札の中身を見て強いカードを待つ」戦略性も生む）
- 山札が尽きた場合は捨て札をシャッフルして山札に戻す
- 種類ごとの詳細な枚数構成は未確定（要テストプレイ調整）

## 4. 被疑心ポイント

- カード使用（疑う/擁護など）によってプレイヤーごとに蓄積されるポイント
- 投票を直接決定づけるものではなく、判断材料・下記イベントのトリガーとして扱う
- 活用方針（A・B路線で確定）
  - A：一定値を超えるとカード使用に制限がかかる（強い擁護カードが使えなくなる等）
  - B：一定値を超えると強制イベントが発生する（釈明カードを使うか沈黙かを迫られる等）
  - 「被疑心5〜9：通常／10〜14：A発動／15以上：B発動」のような多段構成を想定
- 具体的な数値・閾値は未確定（6章参照）

## 5. キャラクター・疑似プレイヤー仕様

### 5.1 キャラクター管理
- 抽象的な初級/中級/上級ラベルではなく、キャラクターごとに以下を紐づけて管理する
  - 難易度パラメータ：判断の最適性／一貫性チェック（発言・行動のブレの少なさ）／欺瞞の巧妙さ
  - 口調・性格（セリフパターンの選択に使う）
- 難易度パラメータは、行動を決めるロジック（戦略判断）の中で確率・閾値として使用する

### 5.2 行動・セリフの設計
- 行動決定は、被疑心ポイント・イベントログなどの構造化データに基づく条件分岐で行う（LLM不使用）
- **セリフはカード使用と同時に発生する**（疑うカードを使えば疑いのセリフ、疑いをそらすカードを使えば弁明のセリフ。カードを使わなければ発言しない＝沈黙も戦略のうち）
- セリフは「行動の種類 × 状況（被疑心の数値など）× キャラクターの性格 × 同条件内の複数候補からランダム選択」の4層構造で管理する
  - 状況条件は複数条件を組み合わせられる形にし、一致度の高いセリフを優先（未作り込みの部分は汎用セリフにフォールバック）することで、作り込み度に比例して自然に賢くなるようにする
  - セリフ内に対象名などの変数（例:「{相手}が怪しい」）を埋め込み、バリエーションを節約する
- セリフはあくまでそのキャラクターの主観・目線で表現する

### 5.3 疑いの理由表示（作り込み対象）
- キャラクターが「なぜ特定の相手を疑っているか」の根拠を、ゲーム内で目に見える形で表示したい
- セリフ（①感情的な短い発言）と、理由表示（②論理的な判断根拠）を2層に分けて扱う
- 理由表示は、そのキャラが**表向きに主張する理由**を出す（人狼・狂人の本心＝戦略的意図はシステム内部に隠し持ち、表示はあくまで建前とすることで、理由表示から正体がバレないようにする）
- 判断根拠の分類（案）：
  - A. 行動の矛盾・変化（態度の急変、発言と投票の食い違い、COと行動の矛盾）
  - B. 自分との関係（自分を疑った相手への警戒・仕返し、擁護してくれた相手への信頼）
  - C. 場の状況（最多被疑者への同調、あえての擁護、大人しすぎる相手への違和感）
  - D. 役職・陣営（占い結果に基づく確信、人狼・狂人の戦略的な疑い＝本心と建前が異なる）
  - E. 漠然とした根拠（明確な理由はなく被疑心の蓄積のみ＝「なんとなく気になる」）

## 6. 未確定事項（今後の検討課題）

### ゲームバランス・数値
- 人狼が複数いる場合の1晩の襲撃可能人数（「1晩1人まで」を基本としつつ、人数の恩恵を殺す人数ではなく襲撃の成功率・確実性や議論での余力に反映する案を検討中）
  - これに連動して、護衛突破カード（人狼複数時に護衛を無視して襲撃を成立させるカード）の採否を決める（襲撃1人までに確定する場合は採用する方針）
- 被疑心ポイントの投票・イベントへの結びつけの具体的な閾値
- 狩人の護衛カードが「強制使用」かどうかの最終確認（占い師の占いは強制で確定済み）
- 占い申告（CO）時に被疑心変動などの副作用を持たせるか
- 基本カードの山札の詳細な内訳（種類ごとの枚数）
- 村人専用カードの具体的な効果・コスト（強すぎない範囲。「結束カード」＝村人が多い試合ほど効果が引き立つ案、「投票観察カード」＝特定1人の投票先を覗ける案を検討中）
- 希少カード（保留枠）として、人狼の「疑いを逸らすカード」以外に何を該当させるか
- カードのコスト・コストプール上限などの具体数値全般（要テストプレイ調整）

### 仕様
- 投票の公開範囲（得票数のみ公開＝非公開ベースが仮候補。村人専用の「投票観察カード」で特定1人の投票先のみ覗ける折衷案を検討中）
- 夜の演出（BGM・背景演出など。結果を明かさない範囲で緊張感を出す）

### 将来対応
- 村人の小役職への細分化（村人枠のプレイヤーそれぞれに簡単な役割を与える。開発がある程度進んだ段階で優先的に着手したい）
- 第三陣営（妖狐など）の追加
- 生成AI（LLM）の導入（当面は不使用。将来必要になった時点で検討）
- 通信方式：当面は通常のHTTP通信（フロント側で疑似タイピング演出）。将来的にWebSocketでのリアルタイム発言表示も選択肢として保持
- フロントエンド方式（Thymeleafベースか、API＋JS/フロントエンドフレームワークか）は未確定

## 7. 役職割り振り（1人プレイ／少人数プレイ対応）

- 対戦構成は「対戦モード」という抽象概念の上に構築する。モードごとに「中核役職（対抗陣営の生命線）」と陣営構成を定義し、通常モードの人狼もその一例として扱う（将来「村人陣営 vs 第三陣営（人狼なし）」のような構成にも対応するため）
- 中核役職（通常モードなら人狼）は、人数に応じて自動調整する特別枠とする（例：5〜7人→人狼1、8〜10人→人狼2、11人以上→人狼3、は仮の目安）
- 占い師・狩人・狂人などのオプション役職は、プレイヤーが「確定で入れる」「ランダムで入れる（いないかもしれない）」「入れない」を個別に設定できる
- 残りの枠は村人（ベース役職）で自動的に埋める
- 確定役職の合計人数が総人数を超える場合は、理由付きのエラーを表示する
- プレイ人数はなるべく増やせるようにする方向。MVPの目安は5〜7人（人間1＋疑似プレイヤー4〜6）、将来的に上限拡大を検討（一般的な人狼ゲームの標準は7〜13人程度）

## 8. システム構成・非機能要件

- バックエンド：Java / Spring Boot
- DB：MySQL
- 通信方式：通常のHTTP通信（Spring Web MVC）を基本とする。フロント側で疑似タイピング演出を行う
- フロントエンド：未確定（Thymeleafベースか、API＋JSフレームワークか）
- 想定規模：初期は小規模（個人利用〜数人程度）を想定。大規模なスケールは将来別途検討
- 中断・再開：各ターンの境界でゲーム状態（構造化データ）を永続化し、いつでも再開可能にする（既存のデータ設計をそのまま流用でき、新規の仕組みは不要）
- 運用コスト：生成AIを使わないため、API利用料は発生しない（サーバー・DBの運用コストのみ）
